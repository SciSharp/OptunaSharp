## How this run works

1. Pick the next direction from the queue below and mark it **in progress**.
2. Read the Optuna source (and, for the commit review, the whole OptunaSharp commit) for the area; run Python first and
   record what it does.
3. Run the same inputs through OptunaSharp (a scratch probe console that references the built Core), diff. For the
   performance commits of `master..main`, which all claim "same trials", a second oracle is available: the same probe
   built against `master` (a git worktree on C:), so any `master` vs `main` difference is a regression candidate,
   then confirmed against Python.
4. Every confirmed difference becomes a finding (ID `QA-n`), with severity, a reproduction test and an explanation.
5. New ideas go to the queue; a direction that needs an owner decision is **paused** with its question listed under
   "Questions for the owner".

Severity: **HIGH** = wrong results/crash on a common path; **MEDIUM** = wrong results/messages on a less common path;
**LOW** = cosmetic or exotic-input divergence; **NIT** = message wording only.

Dedupe rule (lesson of the previous run): before calling a finding new, grep the previous journal's findings table and
the catalog review notes (`K:\catalog\optunasharp\notes\release-review-2026-10-2*.md`, Open items 17–32).
